# E1 technical design

## Context and boundaries

The preview's `present-pump-payment` rule gates Owen's account change on his initial account and both inspected records. Mara's `mara-source` facet requires her own initial account. These provide one originating turn and one receiving turn with independently verifiable permissions. Use the same `prepareDialogue` / `commitDialogue` path as other interviews. Keep case facts, options, mood, evidence, disclosure, endings and browser transport under their existing owners. [Preview package](../../../src/cases/greyhaven-preview.js), [dialogue policy](../../../src/dialogue-policy.js), [engine](../../../src/game.js).

## Decisions

**One director choice with consequences for two witnesses.** Offer exactly two whole strategies on the first authorized payment transition. Both are available under either player history. The director weighs whether recent play emphasizes testing sources or pressing witnesses and selects the interview approach. The engine maps its choice to two reviewed acting instructions. Selecting a strategy neither changes the resolved core nor sends testimony between witnesses. A second independent tone roll would lose this observable connection.

| Strategy | Owen's instruction and local choices | Mara's instruction and local choices |
| --- | --- | --- |
| Invite an account | Take ownership of the explanation. Choose to invite a follow-up or acknowledge the detective's question before answering. | Keep the conversation open. Choose to invite one precise question or offer to hear the detective out. |
| Set a boundary | Insist on precision. Choose to narrow the question to the work or ask the detective to distinguish two questions. | Hold the interview to a specific observation. Choose to request a narrower question or reserve judgment about the detective's inference. |

Author eight reviewed speech-only performances in pilot-specific presentation data (two strategies × two speakers × two reactions). Each combines a conversational move with the full existing body for that target. For instance, Owen's “Ask me about the work after I've answered” invites a follow-up, while Mara's “Which part would you like me to take first?” invites precision. These are proposed acting examples, subject to editorial review alongside the complete answer. Reject a move that adds an observation, identifies guilt, turns hearsay into certainty, promises an unavailable action, or differs only in punctuation or synonyms. A fixed direction determines the pair of choices. The NPC model resolves the remaining choice. The player can proceed with any existing available action.

**Role projections.** Compose both adapters around one existing OpenAI client/model. Use strict structured output, no retries, no stored conversation, and per-role instructions. For the director, project the public Owen→Mara role sequence, last four committed coarse action tags in order (such as inspection, source clarification, challenge, ordinary account), and two strategy IDs. Maintain a bounded per-investigation event list updated on successful inspections and committed substantive interviews only. Each director input has two viable choices, even when one is a better fit for the observed behavior. Return exactly one offered enum in a one-field object, bounded to 256 UTF-8 bytes. The server validates shape and membership independently at the adapter and engine boundary.

For the NPC, use existing style, demeanor, intent and two offered complete pairs, plus the public role, direction, safe acting goal and up to two same-speaker tags (prior account given, prior clarification, repeat). Derive these from committed per-NPC state. Owen's acting goal is to explain his own work in concrete terms. Mara's is to keep the conversation measured and specific. Hand-author these projections independently of private motivations. Each NPC returns the exact narration/dialogue pair under the existing 4 KiB validator. The engine derives the reaction label from the accepted pair. The director never receives candidate lines. The two agents' private contexts never contain each other's memory. [NPC adapter](../../../src/npc-performance.js), [dialogue state](../../../src/dialogue-state.js).

**Transaction.** Resolve, authorize, and prepare the ordinary offline turn first. Allocate one deadline and pending candidate. Validate the director selection, build the actor offer for the authorized core, then validate the NPC result against that offer. Retain the baseline candidate until both results pass. Stage the selected delivery and a one-use follow-up in the same candidate. Immediately before commit recheck speaker, current option/core, policy revision, location epoch, generation, session reservation and exact pair. On failure of a role, commit the baseline candidate only if still current. If authority is lost, discard both alternatives. An HTTP disconnect follows existing admitted-command rules. Cancellation here means actual engine invalidation.

Store the handoff in private investigation state, tied to the case version, recipient and exact facet. A committed handoff survives ordinary travel between rooms. It expires on two intervening committed substantive interviews, replacement/closure/expiry of the session, or loss of target eligibility. Check the target before counting an intervening turn. Ignore non-substantive guidance. On a valid target turn, consume on commit even when the NPC uses fallback. Stale or canceled work neither installs nor consumes a handoff. Revalidate eligibility on use. Bypass provider-selection caches for pilot turns so an earlier prompt cannot masquerade as either role's decision.

**Routing and budget.** Propose a server/CLI environment switch `GREYHAVEN_AGENT_PILOT=1`. With the switch off use existing behavior, including the ordinary optional performer. With it on, only the selected preview uses the pilot. Other preview turns use their existing offline deliveries, which makes the whole-session budget predictable. Other cases keep their current routing. A shared factory must also work through the HTTP session registry. Roll back by disabling the switch and starting fresh sessions. No public API change, migrations, new packages or services are needed.

Start one monotonic four-second timer per directed turn. Allocate at most 1.5 seconds of that to the director. Give the NPC only the remainder. Race a provider that ignores cancellation, abort on expiry, refuse dispatch after the deadline, and reserve each role's one attempt at dispatch even if its result is later discarded. The three session attempt slots are operational accounting, separate from transactional game memory. Insufficient slots, invalid outputs, refusal or a spent deadline produce baseline delivery. An originating fallback creates no direction. Pending work cannot hold the session until a second independent timeout.

## Risks and evaluation

The E1 NPC response schema enumerates the current speaker's offered dialogue strings. All pilot offers have null narration, so the enum describes exactly the approved whole pairs. Adapter and engine each check membership. The engine derives the reaction ID only after acceptance. The local trace records the rejection stage and a fixed category on fallback. It omits provider text and exception messages. See the [Mara rejection diagnosis](../../../docs/greyhaven-e1/README.md#mara-rejection-diagnosis--22-november-2026).

The main risk is writing two labels for what sounds like the same answer. The [demo rubric](demonstration.md) tests choices at constant testimony, varies the director while holding the world fixed, and compares acting moves with labels hidden. Inspect provider payloads with independent forbidden canaries. Record only role, approved category, elapsed time, call count, token totals and actual source in the local demonstration trace. Use the existing local walkthrough pattern with synthetic fixtures in CI. One genuine three-call trial establishes live wiring. A live selection can legitimately repeat an earlier choice, so scripted counterfactuals establish the full range.
