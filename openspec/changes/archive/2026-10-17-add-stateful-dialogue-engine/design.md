## Goals / Non-Goals

**Goals:** one authoritative dialogue path, bounded state, distinct useful offline voices, semantic provenance and additive adapter compatibility for future 8-12-character cases.

**Non-Goals:** changing murderer/evidence/alibis, new private facts, new cast/cases, relationship graph simulation, NPC-to-NPC knowledge propagation, movement, trust-unlocked secrets/confessions, arbitrary natural-language understanding, databases, agent frameworks or critic. Protective behavior applies to established subject boundaries; do not invent who protects whom.

## Decisions

### 1. Three ordered changes and common engine authority

Implement/review `add-stateful-dialogue-engine` first (fully offline engine + HTTP/CLI), then `add-safe-npc-performance` (optional model delivery), then `add-hybrid-dialogue-interface` (cinematic client). Each requires implementation approval and its own checks. Phase 1 preserves the current browser via text; the eventual user-facing milestone is complete only after all three. No feature framework is needed.

Add small plain-ESM server-only authored-dialogue, resolution and state helpers around createInvestigation, rather than a second conversational agent. Keep case.js original content intact; a separate catalog keyed by case/suspect/response IDs contains approved delivery profiles, response variants, evidence mappings, clarification and comparison nodes. Generic machinery iterates data; existing validateCase's three-suspect MVP assertion is not the generic dialogue validator. Custom public-only test cases without dialogue records remain readable with empty dialogue contexts; missing content must not synthesize testimony. Validate catalog references, stable IDs, bounds and prerequisites on construction. New real cases/cast remain future work; test synthetic eight/twelve-NPC catalogs for extensibility and isolation.

All inputs normalize to an engine intent: topic, clarify, revisit, present_evidence, compare_testimony, or social_challenge. The engine selects an authorized response plan, then delivery, then commits. CLI/API/UI never pick claim IDs or bypass predicates. Keep askSuspect(id, question) as the text facade; add a shared dialogue-command entry for choiceId. Accusatory questioning is a social challenge, never a final accusation. Only resolveAccusation with confirmed:true can end play.

| Ben | Blunt, proud, easily provoked | Short practical gardening vocabulary at baseline; under questioning pressure, nervous corrections and bounded over-explanation while retaining directness; not always timid | Baseless accusations irritate more than Alice; relevant reviewed evidence may unsettle; shifting stance/open palms, not invented work/tool actions |

State models detective rapport only; no invented family bonds, favors, protective relationships or hidden affiliations. Variation tests use the same approved social-challenge intent across all three and verify useful topic answers as well as different style; different names alone do not pass.

### 3. Authored semantics and useful hybrid flow

Assign stable server-only claim/testimony IDs to the 18 existing response cores, including authorized lies. Add delivery variants that preserve each core verbatim initially, with reviewed nonfactual framing, rhythm and optional narration. Each core has at least two authored delivery choices, including the unchanged original speech; each NPC also has reviewed social-challenge and clarification deliveries. No new alibi, clue, relationship or factual implication in framing. Repetition can change framing/narration while retaining the same factual core. Semantic equivalence of future rewritten cores requires separate content approval; no validator can infer it automatically.

Resolution order: validate lifecycle/identity/presence/input; resolve explicit available choice; otherwise recognize explicit evidence mentions, contextual clarification phrases, social challenges, then existing topic patterns. Specific evidence/follow-up resolution precedes broad words such as "when"; ambiguous multi-topic or ungrounded follow-ups yield concise guidance plus useful available options, not an invented interpretation. Keep current six canonical example questions recognized. Free text is first class but not unrestricted semantic understanding. "What do you mean by that?" refers only to the last accepted substantive turn with this NPC; no context means guidance. Clarification re-expresses/repeats only that core and cannot disclose its hidden truth. Questions may contain unverified claims, but claims do not become facts or knowledge. Unsupported requests are guidance, never testimony.

Successful engine inspection through either trusted or public method adds an evidence ID to an inspected set; failed/remote/ended inspection does not. Existing clue summaries remain globally visible; inspection gates presenting a clue, not its existence. Generic evidence-topic questions remain available as existing approved general answers; explicit requests to present a named clue require inspection even if it is already named by the player. Relevant mappings are authored (e.g. Ben/footprints and Clara/cufflink); do not invent a contract-specific confession. Clara/contract may use her existing partnership/motive denial with the inspected contract's literal statement as player evidence, without resolving ownership or guilt. Irrelevant evidence gives safe guidance with no invented expertise or confirmation.

Suggestions are engine-authored nodes filtered by current room/lifecycle, inspection, previous testimony and approved prerequisite predicates. Return at most six, prioritizing eligible new follow-up/evidence/comparison options, then unanswered topics and revisits; every supported topic remains reachable through free text and revisits rotate deterministically. No random unlocks or client inference. Initial nodes include topics and the harmless hiding-something challenge. After a reply, a clarification/revisit becomes possible; after relevant inspection, presentation appears. Labels must reveal only currently approved public/testimony information.

An established contradiction means an authored inconsistency between recorded testimony and inspected evidence/other recorded testimony, never a truth verdict inferred by AI. Initial contradiction: Alice's recorded sighting of Clara coming from the garden shortly before the alarm versus Clara's recorded denial of being near the garden after dinner. Both testimony records must exist; the engine establishes conflicting accounts, not which speaker is truthful. Confronting Clara reuses her existing sighting denial. The other NPC's statement remains attributed testimony presented by the detective, not newly confirmed NPC knowledge. The torn contract plus Clara's profitable-partnership testimony supports a contextual evidence question, but profitability and planned dissolution are not logically contradictory by themselves; do not label that pair a proven contradiction. All responses remain existing permitted denials, not new confessions. A player merely claiming a contradiction creates none. Do not treat Alice's sighting/private-route difference or the V engraving as proven ownership/guilt. No automatic culprit scoreboard.

### 4. Bounded state and deterministic emotional rules

Per investigation: inspected IDs and established public comparison IDs, limited to finite authored catalogs. Per NPC: eight recent accepted turns; last substantive testimony pointer; saturating repeat counts 0-3 per authored intent/core; discussed/presented IDs restricted to catalog size; last two narration IDs; three integer dimensions 0-4: cooperation, irritation, tension. Baselines: Alice (2,0,1), Ben (2,0,0), Clara (2,0,0). Tension reflects conversation pressure, not guilt. No numerical states or trigger tables go public.

Each recent turn retains monotonic turnId, normalized intent/core reference, displayed player question/choice label (max 1,000 Unicode characters, tagged as player input), committed narration/dialogue and optional presented evidence ID. Raw player text is never passed to model prompts or promoted into canonical state. Older turns leave the ring; discussed/presented summaries and testimony provenance remain finite IDs. Canonical NPC knowledge and authorized lies never mutate from these records. No model-written memory summaries. The browser may retain its already-received longer history until session replacement; server GET only promises the bounded window.

Apply deltas once per committed substantive turn, clamp 0-4; combine independent tags, maximum one application per tag per turn:

| Deterministic tag | Alice delta (cooperation, irritation, tension) | Ben | Clara |
| --- | --- | --- | --- |
| Repeat an already answered intent/core | (0,+1,+1) | (0,+1,0) | (0,+1,0) |
| Baseless social accusation (no presented relevant evidence) | (0,+1,+1) | (-1,+2,+1) | (-1,+2,0) |
| First presentation of relevant reviewed evidence | (0,0,+1) | (0,0,+1) | (0,+1,+1) |
| First respectful substantive question on a new core | (+1,0,0) | (0,0,0) | (+1,0,0) |

Respectful means a small documented deterministic marker rule ("please"/"thank you") without an accusation tag, not model sentiment. Repeating courtesy cannot farm cooperation; repeated evidence is not first presentation. No per-clock decay or random state. Unsupported guidance, failed commands, canceled final accusation, travel and inspection alone do not change NPC demeanor. Clarification does not count as hostile repetition; repeat tags apply to topic/revisit/presentation, not plain clarification. States affect framing/narration/conciseness only, never core disclosure or option fact prerequisites. Even irritation 4/cooperation 0 must provide an available approved answer.

Public demeanor is one reviewed label: irritation >=3 -> "irritated"; else tension >=2 -> "uneasy"; else cooperation >=3 -> "receptive"; else "neutral". Express fear/amusement/uncertainty only through reviewed situational catalog permissions, not hidden guilt or private relationship. No confession threshold. Avoid last two narration IDs; include null narration in every delivery pool so gestures are not compulsory.

### 5. Structured public contract and HTTP compatibility

Question result adds fields while retaining kind/topic/text/cached where applicable:

```json
{"kind":"answer","topic":"alibi","text":"I was at home in my room all evening.","cached":false,"turnId":1,"narration":null,"dialogue":"I was at home in my room all evening.","demeanor":"neutral"}
```

text equals dialogue; no narration mashed into speech. Unsupported results use kind:"unsupported", topic:"unsupported", narration:null, dialogue/text equal fixed guidance, no substantive turnId. Public state adds `dialogue: { inspectedEvidenceIds: [], conversations: [{suspectId, demeanor, recentTurns: [{turnId, question, kind, topic, narration, dialogue}], options: [{id,label,kind}]}] }`. Conversations cover authored NPCs; remote/ended NPC options are empty, but actual past testimony remains readable. Only successfully committed substantive turns enter recentTurns. Turn IDs are per investigation, monotonic, no gaps for rejected work. Options kinds are topic/clarify/revisit/evidence/contradiction/social; IDs are bounded opaque public slugs, never private claim/policy IDs. Old turns do not become verified facts through projection. Demeanor initially neutral for all; no private baseline export.

Keep POST /questions accepting exactly existing `{suspectId,question,expectedRevision}` or new `{suspectId,choiceId,expectedRevision}`. Exactly one input, slug <=64 for choice, text 1-1000 Unicode chars; reject extra keys or forged state/history/evidence/intent fields. Recompute eligibility in engine at execution, never trust label/ID availability from client. A well-formed unknown/ineligible choice gives 409 dialogue_option_unavailable with a fixed message and no state/revision change; malformed body remains 400. Text attempting uninspected evidence presentation gets accepted unsupported guidance with no substantive memory/emotion mutation (HTTP revision advances once as existing guidance contract); it does not auto-inspect. No new routes are needed. Accepted cached/guidance/choice commands increment revision once, reads/rejections never do. Preserve 16 KiB/100 sessions/30 minutes/four questions/local-origin limits, error envelope, model-key privacy and bearer handling.

Explicitly project nested fields at engine, API and later client; no record spreading, raw model response, private truthfulness/concealment metadata, counters, knowledge, prompt, internal IDs or secret-dependent availability. On ending: options empty, history/demeanor frozen, final result stable; no new questions, inspections or travel. Wrong accusation still does not reveal actual murderer.

### 6. Atomic asynchronous commit

Do not mutate memory, emotions, cache, testimony pointers or presented IDs before async delivery finishes. Prepare an immutable candidate next-state/result and capture engine command generation/location epoch. For direct engine concurrent dialogue, reserve one pending dialogue command; a second returns session_busy. Synchronous travel, inspection or final accusation can invalidate a pending candidate through a shared engine mutation generation; leave-and-return also invalidates. Cancellation may invalidate a candidate as an accepted engine command but cannot change personality or lifecycle.

For HTTP, keep the existing session reservation and revision. Add a narrow staged-dialogue operation: prepare/await candidate, validate session identity/reservation/revision, ask the engine to validate active/generation/presence, build/project candidate result and candidate public snapshot, then synchronously install candidate engine state and increment transport revision in the same no-await commit block. A failed projection, guard or provider completion must not partially install state. Candidate handles are engine-owned, single-use, never serializable; adapters cannot edit next-state or bypass validation. The direct ask facade uses the same candidate/commit path without transport checks. Do not introduce a generic transaction framework.

Provider failure while context remains valid commits deterministic fallback exactly once. End/movement/session replacement/revision mismatch discards both successful and failed delayed completions and all associated changes; abort is best-effort resource cleanup, never the safety proof. Disconnected but admitted HTTP commands can still commit once if guards remain valid, as today; GET returns bounded committed history for deliberate recovery, never automatic replay. A client timeout is not rollback.

Cache only immutable validated performance keyed by catalog version/NPC/core/variant/demeanor permission pool, never skip intent/memory/emotion processing on a hit. Bounded by authored combinations with at most 64 entries per NPC (evict oldest); no raw questions in keys. All cache writes share the candidate commit. cached indicates performance reuse, not "same response for every repeated topic".

### 7. Compatibility and test migrations

Production default is deterministic stateful delivery in phase 1; phase 2 wires the safe performer. Retain the existing explicitly injected legacy `phraser` seam for compatibility tests/callers, including its original topic-string caching and exact fallback. It still passes through shared presence/lifecycle/commit guards and cannot authorize new facts/options/actions; it returns legacy text with narration:null. This trusted legacy seam retains its documented weaker generated lead-in guarantees, is never selectable over HTTP and is not used by the new configured runtime. Reject simultaneous legacy phraser/new performer configuration. Do not claim the new safety guarantee for arbitrary in-process injected code, just as raw data APIs are trusted.

Preserve all independent HW5 A/B/C, timeout and prompt-immersion expectations and historical logs. Existing explicit-phraser cache regressions continue testing the legacy contract; add stateful tests for repetition variation and immutable core facts. Migrate exact public-view fixtures in public-view/lifecycle/HTTP/browser tests for the new dialogue block and inspection mutations. Retain original checks; compare immutable directories separately from deliberately stateful inspection/history. Generic named-evidence classifier unit behavior remains; engine integration now differentiates presentation from a generic evidence-topic request. Update its cufflink-at-Ben expectation to safe uninspected/irrelevant guidance and add a general-evidence test preserving original approved answer. CLI scripted input sequence and yes/no behavior remain: plain text behaves as today; `/choices` inside the existing question prompt displays options and accepts a subsequent choice without inserting a prompt into normal play. CLI renders narration separately when provided.

The room test's checksum strips only existing spatial/dossier additions: keeping original case.js records unchanged preserves it. Test new catalog derivations separately against canonical cores, including the debt disclosure decision. Tests must assert whole-memory/emotion/cache immutability for rejected/stale work, not only lack of visible response.

## Risks / Trade-offs

- [Authored content can itself disclose too much] -> explicit claim/source review, dedicated Alice debt boundary fixtures and user approval; issue #3 remains open.
- [Finite variants limit improvisation] -> quality-reviewed voices, contextual options and varied delivery; do not pretend exact allowlists permit unrestricted prose.
- [Regex understanding is finite] -> deterministic ambiguity guidance, useful choices and clear follow-up resolution; model never chooses facts.
- [Rapport resembles a guilt meter] -> public coarse conversation-only labels, no murderer-based deltas or secret-dependent triggers, no disclosure thresholds.
- [Memory/commit complexity] -> staged single-use candidates and barrier tests for direct/API cached, fallback, projection-failure, movement and ending races.
- [Bounded history loses old wording] -> retain finite testimony references for comparisons, explicitly document eight-turn retrieval and browser-local longer history; no persistence claim.

## Migration Plan

After approval, implement engine/catalog and offline contract first, then commit-safe adapters and CLI, then complete Node verification. Current browser ignores additive fields and continues to use text. Run all automated Node tests, existing browser journeys, build/privacy checks where affected, strict change validation and diff checks; append actual results and mark tasks only after passing. Later phases use this exact contract. Sessions are ephemeral and cannot survive process deployment; no data migration. Rollback code/runtime to prior version and restart local sessions; do not rewrite evidence, history or earlier specs.
